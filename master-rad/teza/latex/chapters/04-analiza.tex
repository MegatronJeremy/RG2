\chapter{Analiza}
\label{ch:analiza}

This chapter evaluates the system. Every number reported here is produced by a measured run.

\section{Metodologija}
\label{sec:metodologija}

\paragraph{Hardver: cross-vendor postavka.} The central evaluation compares the identical pipeline on
two current-generation GPUs from different vendors: an AMD Radeon RX 9070 XT (RDNA4) and an NVIDIA
GeForce RTX 5070 (Blackwell). Both run the same engine binary, the same HLSL-compiled SPIR-V shaders,
the same render graph, and the same scene and settings; the only variable is the selected physical
device. That identity is the fairness basis of the comparison: any difference in timing is due to the
hardware and its driver, not to a different code path. Table~\ref{tab:gpus} lists the relevant
specifications. Because both devices run identical shaders and an identical render graph, the quality
metrics are not expected to differ materially across them; the cross-vendor result is therefore a
performance comparison, and a quality divergence would point at a non-determinism worth investigating
rather than at a real difference. The one documented exception to the identical-code-path claim is
opacity micromap support, discussed next. The static occupancy analysis (Section~\ref{sec:occupancy})
covers both of these adapters and is reported alongside the timings, since register pressure is part
of why the same shader costs what it does on each.

\paragraph{OMM support disparity.} The ``identical code path'' claim above has one exception. Sponza
carries three MASK-mode (alpha-cutout) materials; a cutout mesh traces through the opacity-micromap
BLAS on a device exposing \texttt{VK\_EXT\_opacity\_micromap} and through the any-hit alpha-test
fallback otherwise (Section~\ref{sec:accel}). On the test machines the NVIDIA RTX 5070 driver exposes
the extension and the AMD RX 9070 XT driver does not, despite comparable RDNA4/Blackwell hardware
capability, so the two vendors resolve masked geometry through genuinely different acceleration-structure
code for this scene. The disparity only changes how a masked microtriangle is classified during
traversal (skipping the any-hit shader when OMM marks it opaque or transparent, running it when
unknown); it does not change ray direction, hit position, or shading, so it cannot explain any
quality-metric difference. It is a small, one-directional, driver-dependent contributor to the
per-effect GPU-ms gap wherever a shadow, AO, reflection, or GI ray actually hits cutout geometry in a
given viewpoint, and this evaluation does not isolate it further.

\paragraph{Scena.} The test scene is Sponza, a standard interior with strong indirect bounce, lit by
five enabled lights: four point torches and one directional sun. Three spot lights and two further
point lights are authored in the scene but disabled, and the distinction matters because the default
shadow path costs one ray per light per pixel. Every measurement in this chapter renders at
$1915 \times 1064$. A code-generated stress scene (a grid of meshes) is available for scaling tests.

\paragraph{Controls for fair comparison.} Several controls keep the measurements honest and
reproducible. The camera is held static for every A/B comparison: a moving camera desynchronizes the
frame sequence between two runs and fabricates differences that are timing artifacts rather than real
effects. The shader cache is cleared before any GPU metric is trusted, since a stale cache produces
nondeterministic results. Performance baselines are per-machine and per-resolution, because absolute
milliseconds are not comparable across GPUs or output sizes. Persisted console variables are ignored
during a benchmark run so that a leftover setting cannot silently change the configuration.

\paragraph{Performance measurement.} Each render-graph pass is wrapped in a GPU timestamp scope, and
a harness (\texttt{perf-bench}) averages those per-pass timings over a fixed frame budget once the GPU
has reached a steady state. The steady state is detected rather than assumed: sampling begins when the
peak-to-peak spread of a rolling thirty-frame window of whole-frame GPU time falls below 5\% of its
mean, capped at 600 frames, after which the run proceeds and records that it did not settle. This
matters more than it sounds. A fixed short warmup, which is the obvious implementation, measures part
of the clock ramp: on this scene the frame time takes about fifty frames to settle, so a fifteen-frame
warmup would average the ramp into the result, and how much of it depended on how warm the machine
already was, with nothing in the output to indicate it. The benchmark sweeps a fixed
matrix of configurations, \texttt{rt-off} $\rightarrow$ \texttt{shadows} $\rightarrow$ \texttt{+ao}
$\rightarrow$ \texttt{+refl} $\rightarrow$ \texttt{+gi}, enabling one more effect at each step, so the
cost of an effect is the difference between adjacent configurations. The reason to measure cost as a
difference rather than in isolation is that effects share fixed work: the acceleration structure is
built once, the G-buffer is filled once, and the tonemap runs once no matter how many effects are
enabled. Timing an effect on its own would charge it for all of that shared setup, and the four
figures would then sum to considerably more than the frame actually costs. A difference between two
runs that share everything except one flag charges each effect only for what it adds. That difference is always taken
on \emph{total} GPU time, not a single pass scope. Shadows are the reason: in the default
configuration they are traced inline inside the Forward pass, so they have no scope of their own and
the whole-frame total is the only way to isolate them. Ambient occlusion, global illumination, and
reflections do each run as their own passes with separate timestamp scopes (the first two at half
resolution, reflections at full), and are reported as whole-frame deltas anyway, for consistency
across the table. Table~\ref{tab:pass-cost} gives the per-pass breakdown those scopes provide. A
trailing \texttt{ssgi} configuration swaps the ray-traced GI pass for the screen-space producer on top
of \texttt{+refl}, so it is diffed against \texttt{+refl} rather than against \texttt{+gi}: the two
are alternatives, not cumulative. Across vendors, the raw timestamps are converted to milliseconds
using each device's timestamp period, so the per-pass times are directly comparable; results are
reported for both GPUs side by side rather than diffed against a single-machine baseline, since here
the cross-vendor comparison is itself the measurement.

\paragraph{Quality measurement.} Reconstruction quality is measured against a converged
\emph{path-traced} reference (Section~\ref{sec:pathtracer}): a brute-force unidirectional path tracer
with next-event estimation, accumulated over many frames on a static view, which is the correctness
anchor for every effect at once (shadows, ambient occlusion, reflections, and indirect). For each
real-time technique the harness (\texttt{quality-bench}) captures the same tonemapped present as the
reference and reports three image-quality metrics against it: \textbf{FLIP} (a perceptual difference
metric), \textbf{PSNR}, and \textbf{SSIM}. FLIP is the primary metric because it models what a human
observer notices rather than raw per-pixel error; PSNR reports mean squared error on a logarithmic
scale and structurally favours a blurrier image, and SSIM compares local structure rather than
absolute values. All three are reported so that no single metric's bias decides a conclusion.

The metrics are averaged over three fixed orientations from one interior position (down the nave,
tilted to the floor, and tilted to the upper gallery), chosen to stress ambient occlusion, global
illumination, and reflections differently, so a single framing cannot bias the result. Each capture is
bilinearly resampled to a canonical $1024 \times 576$ before any metric is computed, so a window-size
difference between runs cannot silently change a score. Quality figures quoted elsewhere in this
chapter are the RX 9070 XT's, and Section~\ref{sec:cross-vendor-quality} measures what that costs by
capturing the whole matrix on the RTX 5070 as well.

The two cards do not agree on which effect is most expensive, and that is the more interesting
result. On the RX 9070 XT shadows dominate at \perfEffShadowsAMD{} ms, well clear of reflections and
global illumination. On the RTX 5070 those same three fall within \perfNVSpread{} ms of each other,
which is inside the run-to-run spread, so on that card they are indistinguishable in cost. Ambient
occlusion is the cheapest effect on both. Together the four add \perfFourEffectsAMD{} ms (9070 XT) and
\perfFourEffectsNV{} ms (5070) over their respective baselines, for measured real-time totals of
\perfTotalAMD{} ms (9070 XT, \perfBaseAMD{} ms baseline) and \perfTotalNV{} ms (5070,
\perfBaseNV{} ms baseline).

The half-resolution trace plus denoise is what keeps GI and AO cheap despite their hemispheric
gather. On both cards the screen-space GI producer is cheaper than ray-traced GI at the same point in
the ladder (9070 XT 0.739 ms versus 1.705 ms; RTX 5070 0.667 ms versus 1.309 ms), the expected
screen-space-versus-ray-traced cost tradeoff; Section~\ref{sec:poredjenje} reports the quality side of
that same tradeoff.

Reflections are no longer the most expensive effect, and the reason is a deliberate default change
rather than an optimisation. The reflection à-trous filter measured net-negative and now runs zero
iterations by default (Section~\ref{sec:denoise-eval}), which removed a full-resolution three-pass
chain worth roughly 1.1 ms. That single change is most of the reason reflections no longer lead the
ranking.

The per-pass table explains the ordering. Reflections are the only effect that traces at full
resolution, so their trace alone (1.495 ms on the 9070 XT) costs more than the half-resolution GI
trace, and until the filter was disabled they also paid a full-resolution three-pass denoise on top.
Ambient occlusion is the cheapest despite casting more rays per pixel, because those rays are short
(bounded by \texttt{render.ao.radius}) and terminate on the first hit, while a reflection ray can
traverse the whole scene and then shade what it finds.

Shadows cost what they do for a different reason, and the per-pass table cannot show it because they
have no scope of their own. Comparing the \texttt{rt-off} and \texttt{shadows} configurations pass by
pass on the 9070 XT, the Forward pass grows by 3.482 ms while the raster shadow-map passes disappear
entirely, returning 1.056 ms (\texttt{Shadow} 0.107 and \texttt{PointShadows} 0.949). Those two terms
alone would give 2.426 ms, while the measured whole-frame delta is 2.272 ms; the remaining 0.154 ms is
every other pass shrinking slightly at once, which is the signature of a clock shift rather than of
real savings, and is consistent with \texttt{rt-off} being the noise-dominated configuration on this
adapter (8.3\% run-to-run spread against under 1\% for the others). The honest reading is that the
inline query moves roughly three and a half milliseconds of work into the forward shader and hands
back one, and that the whole-frame difference is the number to quote because the per-pass terms do not
close.

Isolating the signals this way explains a result that the composited frames hide. Toggling shadows,

open, so occlusion is confined to the arcade vaults and the column bases; the raw GI term is dim in
absolute terms yet carries the colour bleeding, the red and green drapes tinting the stone beside them,
which is the contribution a constant ambient cannot reproduce.

\section{Dve strategije za senke: inline naspram stohasti\v{c}ke}
\label{sec:analiza-shadow-strategy}

Section~\ref{sec:senke} describes two structurally different ways to shadow a scene: the default
inline path, which traces one ray per light per pixel inside the forward shader, and the stochastic
path, which picks one light per pixel by resampled importance sampling and reconstructs the result
with the shared denoiser. Their cost curves have different shapes, so which one wins is a property of
the scene rather than of the implementation.

\begin{table}[tbp]
\caption{Dve strategije za senke na istoj sceni sa pet upaljenih svetala (GPU ms, dodatak u odnosu na
\texttt{rt-off}).}
\label{tab:shadow-strategy}
\centering
\input{data/perf-shadow-strategy.tex}
\end{table}

The two cards disagree about which strategy is cheaper, and they disagree in opposite directions. On
the RX 9070 XT the stochastic path wins, 1.723 ms against 2.272 ms. On the RTX 5070 it loses badly,
3.362 ms against 1.294 ms, a factor of 2.6. The same code, the same scene, the same five lights, and
the better technique is the other one depending on the vendor.

The explanation is where each architecture spends its budget. The stochastic path replaces per-light
rays with one importance-sampled ray plus a reconstruction chain, so it trades ray count for filter
cost. That trade is favourable exactly when rays are expensive relative to filtering. On the 5070 they
are not: dedicated traversal hardware makes the twenty coherent inline rays of a five-light scene
cheap enough that paying a temporal pass, three à-trous iterations, and an upsample to avoid them is a
net loss. On the 9070 XT, where traversal is driven by shader instructions and competes with shading
for the same execution resources (Section~\ref{sec:accel-pregled}), the same trade pays.

This is the strongest cross-vendor result in the thesis, and it is stronger than a single-GPU ranking
would have been: it says the choice of shadow technique is a property of the target architecture
rather than of the scene. A renderer that hard-codes either strategy is wrong on one of these two
cards. It also bounds how far a single-vendor evaluation can be trusted, which is the practical
argument for measuring both.

Two caveats bound the claim. The stochastic path's cost is nearly independent of light count while the
inline path's grows with it, so five lights is one point on two curves that must cross somewhere; this
scene cannot show where. And the stochastic producer is experimental and off by default, with known
artifacts under camera motion where two point lights overlap, so these are the numbers of a prototype
rather than of a shipping technique.

The knee sits at 1 ray per pixel. Going from 1 to 8 rays costs \rcGpuPct\% more GPU time
(\rcGpuLow{} to \rcGpuHigh{} ms) for a \rcPsnrGain{} dB PSNR gain and a FLIP improvement from
\rcFlipLow{} to \rcFlipHigh{}, both within run-to-run noise on
this metric. The denoiser and temporal accumulation already recover most of the achievable quality
from a single ray; once they are in the pipeline, additional samples per pixel are not where this
engine's ray budget should go. This is consistent with the SVGF design goal (spatiotemporal
filtering to make 1 sample per pixel viable) rather than a property specific to this
implementation. Figure~\ref{fig:spp-sweep} shows the raw noise this filtering is masking, at the two
extremes of the sweep. The capture disables the GI spatial denoiser, the GI temporal accumulation, and
TAA, and is cut
off at a fixed 30-frame cap. Disabling TAA is what makes the figure honest: TAA is itself a temporal
accumulator, so with it enabled the capture settles into the same smoothness as the denoised image and
the ray count appears to make no difference at all.

Quantifying that needs a measure of per-pixel roughness. Define the \emph{high-frequency energy} of an
image as the mean absolute difference between vertically adjacent pixels of its grayscale channel,
$\frac{1}{(H-1)W}\sum_{y,x} |g_{y+1,x} - g_{y,x}|$, computed on the 8-bit tonemapped capture; noise
raises it, blur lowers it, and it can be recomputed from the committed figures. With TAA enabled, one
ray per pixel and the fully denoised image both score 5.9, which is the measurement saying the figure
would show nothing. With TAA disabled the ray count separates cleanly: 10.8, 9.1, 8.1, and 7.3 for
one, two, four, and eight rays per pixel, monotonically approaching the reference as the sample count
rises.

\section{Polovi\v{c}na naspram pune rezolucije}
\label{sec:halfres}

Tracing the two hemispheric gather effects at half resolution is the single largest cost decision in
the renderer (Section~\ref{sec:rendergraph}), and it is the one sub-question of
Chapter~\ref{ch:uvod} that the preceding sections do not answer. Setting
\texttt{render.gi.scale} and \texttt{render.ao.scale} to 1.0 turns it off, changing nothing else, so
the two configurations differ in exactly one variable.

vreme \texttt{+gi} konfiguracije; kvalitet je meren iz atrijumskog pogleda naspram konvergirane
path-traced reference.}
\label{tab:halfres}

\begin{tabular}{lrrr}

\texttt{AO} prolaz (ms) & 0.17   & 0.63   & $\times 3.7$ \\
\midrule
PSNR (dB)              & 24.89  & 24.91  & $+0.02$ \\

Full-resolution tracing costs 5.49 ms more per frame, a 56\% increase on a budget that was already
approaching ten milliseconds, and returns 0.02 dB of PSNR. All three metrics move by less than the
run-to-run spread, so the correct reading is not \rqt{full resolution is slightly better} but
\rqt{the measurement cannot distinguish them at all}.

The reason is that the denoiser is the binding constraint, not the sample grid. Both configurations
feed the same à-trous filter, whose edge-stopping kernel already blurs over a neighbourhood wider than
the factor of two separating them; the extra samples are averaged away by the very filter that makes
the half-resolution result usable. Tracing four times as many rays only helps if something downstream
can preserve the difference, and here nothing does. This is the strongest single argument in the
thesis for the half-resolution plus bilateral-upsample pattern: it is not a quality compromise
accepted for speed, it is close to free.

That the difference exists before the filter, and only there, is visible in the traced buffer itself.
Figure~\ref{fig:halfres-buffer} shows the raw GI irradiance under both settings, taken through the
debug view that bypasses the upsample, denoiser and composite. The half-resolution buffer carries
44\% more high-frequency energy by the roughness proxy of Section~\ref{sec:raycount} (41.68
against 28.91). That proxy is reproducible where the per-pixel difference is not: a second
full-resolution capture with identical settings scores 28.85, within 0.2\%, while differing from the
first by 18.3 grey levels per pixel simply because the two traces drew different random samples. So
the per-pixel gap of 35.4 between the half- and full-resolution buffers is only about twice the
run-to-run floor and carries little information, whereas the roughness gap is far outside it. Four
times the rays do produce a measurably cleaner buffer; what Table~\ref{tab:halfres} shows is that
nothing downstream of the filter preserves it.

\begin{figure}[tbp]

With temporal accumulation already active, the spatial SVGF pass changes reconstruction quality
against the static-frame metrics (PSNR, SSIM, FLIP) by less than measurement noise: the temporal
history is doing essentially all of the visible convergence at this settled frame, and the spatial
filter's own contribution shows up elsewhere, in temporal stability rather than static quality. A
frame-to-frame RMS delta on the same static view (frame $N$ against $N{+}1$ at steady state, a
flicker proxy under a static camera, not motion) drops only from \flickerOff{} with the denoiser off
to \flickerOn{} with it on, a \flickerPct\% reduction. That figure is sensitive to one protocol detail:
unless temporal history is cleared before sampling, the unfiltered case is credited with noise that
accumulated while assets were still streaming, which inflates the apparent reduction to near 40\%.
Figures captured with and without that clear are not comparable. The GPU cost of the denoiser is best read from its own timestamp
scopes rather than from a whole-frame A/B: the three \texttt{GIDenoise} à-trous iterations total
\perfDenoiseAMD{} ms on the 9070 XT and \perfDenoiseNV{} ms on the 5070 (Table~\ref{tab:pass-cost}), against a full-frame
budget near nine milliseconds. Toggling the denoiser and diffing whole-frame totals gives about 0.07 ms, but that
number should not be quoted: it is smaller than the run-to-run spread of the identical configuration,
so it measures noise rather than the filter. The \texttt{GIDenoise.comp} shader from
Section~\ref{sec:denoising} is inexpensive in isolation, and its cost is amortized further because it
runs at half resolution.

The composited frames above show the denoiser's effect diluted by everything else in the image. The
engine's debug views isolate it exactly: mode 6 is the half-resolution GI irradiance buffer as the
trace leaves it, and mode 7 is the same buffer after temporal accumulation and the à-trous filter,
before either is upsampled or composited. Figure~\ref{fig:gi-denoise-ab} is that pair, and it is the
denoiser's contribution rendered as an image rather than as a table row. The high-frequency energy
defined in Section~\ref{sec:raycount} falls from \hfGiRaw{} to \hfGiDenoised{} between the two, which
is essentially all of it, while the mean level rises because the filter fills in the pixels where
every ray happened to miss.

Putting that next to the table above gives the section its actual conclusion, and it is not the
expected one. The filter transforms the intermediate buffer almost completely, removing some 96\% of
its per-pixel roughness, and yet the finished image is unchanged to within measurement noise and the
static flicker improves by under seven percent. The work is real but the pipeline downstream absorbs
it: the buffer is upsampled from half resolution, multiplied by surface albedo, added to direct
lighting that dominates it, and then run through a temporal resolve that is itself a strong low-pass
in time. At two rays per pixel with temporal accumulation already active, the spatial à-trous is close
to redundant for global illumination, and Section~\ref{sec:denoise-eval} has already shown it is worse
than redundant for reflections. That is why it is kept at three iterations for global illumination and
disabled for reflections rather than applied uniformly, and it is an argument for spending a
reconstruction budget on the temporal side before the spatial one.

\paragraph{Isti filtar na refleksijama je \v{s}tetan.} The same à-trous runs on the reflection signal,
and there it measured net-negative, which is why it is now disabled by default. Turning it off improved
every spatial metric at once: FLIP 0.1742 against 0.1746, PSNR 21.75 against 21.70, and SSIM 0.6473
against 0.6419. That all three move the same way is what separates this from metric gaming, because the
signature of merely deleting blur is FLIP and PSNR improving while SSIM drops, and SSIM improved here.
The structural reason is that the filter is guided by the receiving surface's normal and depth, which
is correct for a diffuse gather but wrong for reflections: reflected radiance is view-dependent, so on
a flat reflective surface those guides are constant and the kernel opens wide exactly where reflected
detail lives. The saving is not marginal either, since the reflection chain ran at full resolution
with no upsample after it: removing it is most of the 1.1 ms by which reflections became cheaper in
Table~\ref{tab:cena}. A roughness-driven kernel remains the structurally right fix, but it now has to
beat filtering off rather than beat three iterations.

\paragraph{Cena filtra nije ista na oba proizvo\dj a\v{c}a.} Rolling the à-trous outer loop, which the
engine did to cut the shader's register pressure (Section~\ref{sec:occupancy}), turned out to pay
asymmetrically. On the RTX 5070 every stride got faster. On the RX 9070 XT it was close to a wash on
the half-resolution GI and AO chains, with the first iteration slower and the last one faster, and it
paid only on the full-resolution chains. The per-pass table shows the residue of this: the AMD denoise
chain is front-loaded (\texttt{GIDenoise0} 0.133 ms falling to 0.089 ms at \texttt{GIDenoise2}) while
the NVIDIA one inverts (0.094 ms rising to 0.127 ms). The stride-1 iteration is the one where adjacent
taps are cache-friendly enough that batching beats occupancy, and that tradeoff evidently lands
differently on the two memory hierarchies. It is a reminder that a shader optimisation justified by a
register count is not automatically a win, and has to be measured per vendor like everything else in
this chapter.

\section{Stabilnost pod kretanjem}
\label{sec:motion}

Every quality figure so far comes from a static camera, and Section~\ref{sec:denoise-eval} already
found that this hides most of what the spatial denoiser does: with temporal accumulation active the
filter changes PSNR, SSIM and FLIP by less than measurement noise, while cutting frame-to-frame
flicker by \flickerPct\%. That argument was made with a flicker proxy on a static view. This section
moves the camera.

The obvious way to build such a measurement is to fly a fixed camera route, capture frames along it,
and score each against a converged path trace of the same instant. That was done, and the first result
it produced is a caution about the method rather than a fact about the renderer. Across the eleven
techniques, the per-frame FLIP measured this way correlates with the static FLIP of
Section~\ref{sec:poredjenje} at $r = +0.99$. It is very nearly the same measurement taken twice.

The reason is structural. A converged per-frame path trace is a sequence of independent still images;
it contains no temporal structure, because nothing in its construction relates one frame to the next.
Error measured against it therefore has no temporal component to carry, however much the camera moves
while the frames are captured. This is not a defect of this implementation but of that experimental
design, and it is a known conflation: k-DOP Clipping \cite{ikkala2024kdop} states outright that a
supersampled reference introduces a constant error by also comparing general temporal-antialiasing
quality against supersampling. The canonical denoiser papers avoid it by reporting accuracy against a
reference and temporal behaviour separately, the latter with a reference-free measure.

Two quantities in the moving capture do carry information the static gate cannot. The first is a
temporal measure that compares how much the technique changes between consecutive frames against how
much the \emph{reference} changes over the same interval, so that motion inherent to the scene is
subtracted and only excess instability remains. Subtracting matters: on this route the reference
itself moves by a FLIP of about 0.09 between adjacent frames, so a naive frame difference would report
that as instability. Ranked by it (Table~\ref{tab:motion}), the techniques order exactly as the
flicker proxy predicted: the fully reconstructed configurations are the most stable and plain
rasterization the least, with the screen-space and single-effect variants between. That is the same
conclusion as Section~\ref{sec:denoise-eval}, reached under motion instead of by proxy, and it is the
evidence for the claim that the spatial filter buys stability rather than static fidelity. The two
temporal metrics disagree usefully: \texttt{rtgi} has the best tFLIP while \texttt{all-rt} has the
best JOD, because tFLIP isolates temporal excess alone where ColorVideoVDP is spatio-temporal and
\texttt{all-rt} is far more accurate spatially.

\section{Kvalitet izme\dj u proizvo\dj a\v{c}a}
\label{sec:cross-vendor-quality}

The cross-vendor argument of this chapter rests on the claim that the two adapters run identical code,
so any difference between them is hardware and driver. Everywhere else that claim is used to justify
comparing \emph{time}. This section tests the other half of it: whether the reconstructed images also
agree. If they did not, a timing difference could always be dismissed as the two cards having done
different amounts of work.

The whole quality matrix was captured a second time on the RTX 5070, giving 33 viewpoint and technique
pairs. Across all 33 the largest absolute difference in FLIP between the adapters is \textbf{0.0037},
the median is \textbf{0.0007}, and 24 of the 33 fall below 0.001. The secondary metrics agree to the
same degree: PSNR never differs by more than 0.10 dB and SSIM never by more than 0.0045. For scale,
the difference this chapter is actually interested in, between raster and all effects enabled, is a
FLIP of \qRasterFlip{} against \qAllRtFlip{}, two orders of magnitude larger than the vendor
disagreement.

Technique quality is therefore effectively vendor-independent here, which means the entire
cross-vendor story of this thesis is cost rather than image quality. That is a useful negative result:
the per-effect timings in Section~\ref{sec:cena} and the shadow-strategy inversion in
Section~\ref{sec:analiza-shadow-strategy} can be read as pure performance differences, with no
accompanying quality caveat.

One methodological detail makes this measurable at all, and the obvious alternative would have
destroyed the result. Both adapters are scored against the \emph{same} path-traced reference. The
reference cache is keyed on the scene, the camera pose, the frame count and the content of the
path-tracing shaders, and deliberately not on the device, so the second adapter reuses the reference
the first produced rather than tracing its own. Had each been scored against a reference it produced
itself, every comparison would have carried the difference between two independently converged path
traces, and there is no reason to assume that difference is small next to the technique difference
being measured. Sharing the reference makes the reference error common to both sides, where it
cancels.

Two limits bound the claim. The residual disagreement is not zero, and the largest of it sits on the
ambient-occlusion and shadow rows, which are also the effects whose rays interact with the cutout
geometry where the two drivers genuinely differ (Section~\ref{sec:metodologija}). That is consistent
with the opacity-micromap disparity being the mechanism, although this experiment does not isolate it.
And the reference is shared here because both adapters were measured on one machine with a warm cache;
on two machines each would trace its own, and the comparison would require transferring the reference
rather than recomputing it.

\section{Zauzetost i cena \v{s}ejdera}
\label{sec:occupancy}

This section reports static shader occupancy: how many registers each ray-tracing and denoising
shader needs, and how many waves the hardware can therefore keep in flight. It is the one place where
the two vendors can be compared on something other than time, and it explains part of the cost
difference the rest of the chapter measures.

Two artifacts feed it, with deliberately different authority. For AMD the offline analyser compiles
every shader and every permutation, so its coverage is complete and deterministic, and it is what the
project gates on. For NVIDIA no offline analyser exists, because register allocation happens inside
the driver's just-in-time compiler; the figures there are read back from the driver itself through
\texttt{VK\_KHR\_pipeline\_executable\_properties} after the pipelines are built. The two agree on
every AMD register count they share, which is what licenses carrying the offline permutation labels
over to the runtime numbers: the runtime capture reports both \texttt{DefaultLit} variants under one
pipeline name and cannot tell them apart on its own.

Only one shader on the render path is occupancy-limited on either card, and it is the same one:
\texttt{DefaultLit.frag} in its inline-shadow permutation, at 127 VGPRs and 10 of 16 waves on the
9070 XT. Compiled without the inline shadow query the same shader drops to 87 VGPRs and full
occupancy, which locates the cost precisely: tracing shadow rays inside the forward shader is what
pushes it over a wave boundary, and that is the same effect Section~\ref{sec:cena} sees as a Forward
pass that grows by 3.482 ms. Nothing in the table spills registers, and across all 47 cooked shaders
exactly one uses any scratch memory at all (\texttt{NeuralConv.comp}, 272 bytes), which is off the
render path.

Figure~\ref{fig:occupancy-cliff} plots why the two permutations land so far apart for a difference of
40 registers. Occupancy is not proportional to register use: it is a step function, because registers
are allocated in fixed blocks of 24 on this architecture and the wave count is the register file
divided by that rounded-up allocation. Between 24 and 96 VGPRs every shader gets all 16 waves, so the
five shaders in the flat region differ in register use by a factor of 1.5 (59 to 87) at no cost in
parallelism.
Past 96 the count falls in steps. The inline-shadow permutation at 127 VGPRs is 31 registers into
that region and allocates 144, giving 10 waves; had it stayed at or below 96, as its non-tracing
sibling does at 87, it would have cost nothing. This is why the table gates on occupancy rather than
on the register count directly, and why a register increase is only worth acting on when it crosses a
step.

The cross-vendor comparison is the interesting part, and it inverts the naive reading. NVIDIA uses
markedly fewer registers for the same shader, 80 against 127 for the inline-shadow variant, yet its
relative occupancy is \emph{lower}: 25 of 48 warps against 10 of 16 waves, 52\% against 62\%. The
reason is the ratio each architecture provides. A Blackwell SM has 65536 registers for up to 48 warps
of 32 threads, which is about 42 registers per thread at full occupancy, so register pressure begins
to bite earlier there than the raw counts suggest. Fewer registers used does not mean more parallelism
available.

Three limits belong with these numbers. The occupancy is theoretical and register-derived, so it is an
upper bound on both vendors and says nothing about what is achieved once memory stalls and other
limits are included; that needs a runtime profiler. The RDNA4 register allocation granularity is taken
from documentation and has not been confirmed against a per-compile report the way the RDNA3 figure
was, so a wave count sitting near a boundary is model-dependent: at a granularity of 8 rather than 24
the inline-shadow permutation would read 12 of 16 rather than 10. And the NVIDIA figure is explicitly
an upper bound, since the allocation granularity for that compute capability is not published and
rounding up can only lower the warp count.

The one statistic deliberately not reported is register spilling on NVIDIA. The driver returns a
\texttt{Local Memory Size} whose upper 32 bits are a constant, so the values differ only in their low
half; the low half is very likely the real figure, but masking it would be inference presented as
measurement, and a plausible fabricated number is worse than a missing one.
